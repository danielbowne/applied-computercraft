# Ship flow

`<base>` is the branch the change targets: `main` unless the work is for a Minecraft-version branch such as `mc-26.2` (for an existing PR, read it from `gh pr view <n> --json baseRefName -q .baseRefName`).

Rules that hold at every step:

- Never commit to `main`.
- Never push before the pre-push review has run (docs-only changes included, unless the owner waives it for that push).
- Never merge without the owner's explicit yes in this session.
- Never merge on a red or stale check (see step 7).

## Order

1. **Branch from fresh origin/<base>.** `git fetch origin && git switch -c <type>/<slug> origin/<base>`. Types: `feat`, `fix`, `chore`, `docs`, `refactor`, `ci`, `build`, `test`, `release`, `perf`. For parallel work, use a worktree under `.claude/worktrees/` (`git worktree add .claude/worktrees/<slug> -b <type>/<slug> origin/<base>`); that folder is git-ignored.
2. **Builder.** Hand a self-contained brief to the `builder` agent (`.claude/agents/builder.md`) or do the work directly. The builder commits on the branch and stops; it does not push.
3. **Gates.** `./gradlew build` with JDK 25. Behaviour changes also get verified on a real NeoForge server with a CC computer next to an AE2 block (see "Testing reality" in `CLAUDE.md`). Lua-visible changes must already carry the README edits (CHANGELOG.md is generated by release-please from commit subjects, so do not edit it).
4. **Pre-push review and fixes.** Run `git fetch origin <base>`, then the `pre-push-review` skill on `origin/<base>...HEAD`. Fix its findings by default; ask the owner only about product decisions or findings you believe are wrong.
5. **Push.** `git push -u origin <branch>`, then confirm with `git ls-remote --heads origin <branch>`.
6. **PR.** `gh pr create --base <base> ...` with a conventional-commit title under 70 characters (it becomes the squash subject, which release-please reads to pick the version and write the changelog line; see the `release` skill) and a body written per the `pr-description` skill (long bodies via `--body-file`).
7. **CI and freshness.** Wait for CI (`gh pr checks <n> --watch`). Stop if the `build` check is red or the branch is behind `<base>`. `mergeStateStatus` reads BLOCKED on this repo for every PR (a review is required), so it never shows BEHIND; check instead with `gh api repos/{owner}/{repo}/compare/<base>...<branch> --jq .behind_by` (0 means up to date) or `git merge-base --is-ancestor origin/<base> origin/<branch>`. If behind, update the branch (`gh pr update-branch <n>`, or merge or rebase `<base>` in and push) and wait for `build` again. Branch protection requires a PR, one approving review, a passing `build` check, an up-to-date branch, resolved conversations and linear history; only squash merges are allowed. `--admin` bypasses all of those, including unresolved conversations, so the discipline here is on us: resolve conversations before merging.
8. **Wait for the owner.** Present the PR and ask whether to merge. Do not merge on your own.
9. **Owner merges, squash only, with an explicit subject and body file:**
   `gh pr merge <n> --squash --admin --subject "<subject> (#<n>)" --body-file <file>`
   `--admin` is owner-only and is used only after `build` is green on an up-to-date branch with conversations resolved. `permissions.ask` prompts on every `gh pr merge`; the `guard-squash-merge` hook is what checks that a squash carries a written body.
10. **Clean up.** First confirm what was merged: `gh pr view <n> --json state,headRefOid` must show `MERGED`, and `git rev-parse <branch>` must equal `headRefOid`. If either differs, stop and tell the owner (the local branch has commits that were not merged). Then, in this order: remove any worktree (`git worktree remove .claude/worktrees/<slug>`), `git fetch origin --prune`, and delete the local branch with `git branch -D <branch>` (capital D: a squash merge never looks merged to git; it cannot be deleted while a worktree has it checked out, which is why the worktree goes first).
11. **Release.** Releases are automatic (release-please). Your PR title decides whether the merge releases: `feat`, `fix`, `perf`, a `!` type or a `BREAKING CHANGE:` footer opens or updates the release PR; `docs`, `ci`, `chore`, `test`, `refactor` and `build` never do. Only the PR title and the merge body reach `main`, so a `BREAKING CHANGE:` or `Release-As:` footer goes last in the `--body-file`. The release PR is opened by release-please (via a GitHub App token), not by you, and the owner merges it with `--admin` (same squash and body-file rule as step 9) once its `build` is green. Merging it is the release; never tag by hand. Follow the `release` skill.

`/ship-it` runs steps 4 to 10 for the current branch.
